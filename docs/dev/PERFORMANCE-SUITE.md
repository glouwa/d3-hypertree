# Performance measurements

The performance suite of d3-hypertree: generated trees in the test harness
(`test/harness.html`) in headless Edge, driven by Playwright (`test/perf/run.mjs`). It
measures the interaction pipeline (load, drag, zoom, pinch, hover, the settling after a
gesture), what each layer costs per frame, what single options cost and what the
library's presets cost, and it keeps three result tables with the same schema so that
a change can be judged against a reference without stashing or rebuilding old code.
The application has the same suite for its real pages
(`hypertree-of-life/docs/PERFORMANCE-SUITE.md`); use that one to see what users get, this
one to see why.

## The three result files

| File | Content | Written by | Rule |
|---|---|---|---|
| [longterm.md](performance/longterm.md) / .json | the long-term reference: many iterations, mean and standard deviation precise enough to see small changes | `npm run perf:longterm` (8 iterations) | **only on the user's explicit instruction**; needs a clean working tree |
| [last-commit.md](performance/last-commit.md) / .json | the state of the last commit (hash in the header) | `npm run perf:commit` (3 iterations) right after committing | only with a clean working tree (`--force` overrides, the header then says "uncommitted changes") |
| [last-run.md](performance/last-run.md) / .json | the last run, whatever the working tree contains | `npm run perf` (2 iterations), `npm run perf:quick` (~1 min, ternary tree, desktop) | overwritten on every run |

All three are generated by `test/perf/run.mjs`; do not edit them by hand. The `.md`
is for reading, the `.json` holds the samples for `test/perf/compare.mjs`.

## Before/after without stashing

1. Commit the state to compare against, then `npm run perf:commit`: that measures
   exactly that commit and writes `last-commit`.
2. Change the code. `npm run perf` (or `perf:quick` while iterating) writes `last-run`
   and prints the comparison with `last-commit` and `longterm`: both means, the change
   in percent, and `*` where the change exceeds twice the larger standard deviation
   and 3 %.
3. `npm run perf:compare -- [a] [b]` compares any two result files later.
4. After committing the change, `npm run perf:commit` again: the new reference.

A quick run measures only a part of the matrix; the comparison then lists only the
rows both files have.

## What is measured

Trees (deterministic generators of `test/config.js`, all with labels): binary 2^10
(2,047 nodes), ternary 3^8 (9,841), wide 8^5 with emojis (37,449), a fan of 200
leaves beside a binary subtree, a deep star (4 arms of depth 40). Modes: desktop
unthrottled; slow = CPU 6× slower with touch (the load is measured unthrottled).
Every group is one table; cells are mean ± standard deviation over the iterations.
Schema: `test/perf/schema.mjs`.

| Group | Rows | Metrics |
|---|---|---|
| Load | tree × mode | ms until the component's initPromise resolved and the first frame is drawn, nodes, visible |
| Idle | tree × mode | frames and main-thread ms in 3 s standing still (should be ~0) |
| Drag | tree × mode | main-thread ms per pointer step (61 steps), frames/sec the JS of the median moving frame allows, filter ms, frames, visible |
| After the drag | tree × mode | frames, main-thread ms and the time of the last frame in the 4 s after releasing |
| Wheel (desktop) | tree × mode | main-thread ms per wheel step (20), frames during, frames and main-thread ms in the 4 s after |
| Pinch (slow) | tree × mode | main-thread ms per touch step (50), frames/sec (JS of the median frame), frames |
| Hover (desktop) | tree × mode | main-thread ms per mouse position (40), frames/sec (JS of the median style frame), style frames |
| Layers | tree × mode × layer | frames/sec each layer alone would allow (1000 / its median ms per moving frame of the drag, from the layer stack's timings); layers below 0.05 ms are left out |
| Features | ternary × desktop × variant | the drag with one option changed: rectangle and half-plane view, icons, multiline labels, filter off, uniform weights, colors, cells off / hidden while dragging, the three label layers, highlight and marker off, keepTreeInView off, straight links, nodes or links off |
| Presets | ternary × desktop × preset | the drag with a library preset (`src/config/presets.ts`): infovis, infovisEmoji, infovisFiles (on the file system fixture), highlightCell, highlightDisk; plus the load time |

Main thread = the renderer's task time from the Chrome DevTools Protocol
(`Performance.getMetrics`, includes style, layout and paint). frames/sec = 1000 / the median JS time of the unit
disk's frame function timed inside the page (filter, layout, layers): the rate the JS alone would allow, not the displayed frame rate. The layer
values come from the layer stack (`layerStack.d3meta`). Requests to other hosts are blocked.

## Running

Requirements: Node and Microsoft Edge. The suite builds `dist/` itself unless
`--no-build` (the tests and the harness load `dist/d3-hypertree.js`).

```bash
npm run perf                      # last-run, 2 iterations, whole matrix
npm run perf:quick                # last-run, ternary desktop, 1 iteration, 4 features
npm run perf:commit               # last-commit, 3 iterations, clean tree
npm run perf:longterm             # longterm, 8 iterations, clean tree, on instruction only
npm run perf:compare              # last-run against last-commit
node test/perf/run.mjs --trees wide --modes slow --features none --presets none --iterations 3
node test/perf/run.mjs --server http://localhost:3100 --no-build   # the playground's server
```

Options: `--iterations N`, `--trees`, `--modes`, `--features all|none|list`,
`--presets all|none|list`, `--feature-tree`, `--label "text"`, `--force`.

## Caveats

- Close other heavy programs; the suite runs one browser at a time but shares the
  machine. Iterations are interleaved (iteration 1 of everything, then iteration 2),
  so a drift of the machine affects all rows alike.
- Generated trees are regular; real trees (the application's suite) have fans, deep
  branches and long labels in other proportions.
- The CPU throttling is an emulation. Headless Edge composites differently from a
  visible window; paint numbers are indicative.
- The `*` mark is a rule of thumb (2 sd and 3 %), not a significance test; with 2
  iterations the standard deviation itself is rough. Use `longterm` for small effects.

## Older benchmarks

[PERFORMANCE.md](PERFORMANCE.md): the trace-based benchmarks `test/bench-layers.mjs`
(marginal cost of each layer incl. browser-native work) and `test/bench-interaction.mjs`
(pipeline phases from a CPU profile), with the numbers and findings of the
modernization phases. They answer *why* a frame costs what it costs; the suite above
tracks *what* it costs over time.
